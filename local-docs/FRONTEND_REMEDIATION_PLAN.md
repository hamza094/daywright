# Frontend Production Readiness Plan

Updated: 2026-10-19

This is the single active frontend plan. It consolidates the API/frontend alignment plan, Phase 1 endpoint matrix, frontend/backend contract remediation plan, and the earlier frontend readiness review. Completed alignment work is intentionally omitted; historical checkboxes are not release evidence.

## Current release verdict

**Not ready to ship yet.** Static review (2026-09-30) and live code inspection (2026-10-19) found launch-blocking frontend defects in task/project editing, form state, CSRF configuration, undeclared runtime globals, WebSocket TLS configuration, and a 2FA session expiry comparison bug. The code audit did not exercise the browser against staging, so the release gate below still requires runtime evidence.

## P1 — Release verification (required before opening production traffic)

### API contract rules

- Wrapped resources: use `getObjectData(response)` or `getResponseData(response)`; paginated collections: use `getPaginatedData(response)`; message-only responses: use `getResponseMessage(response)`; failures: use `parseApiError(error)`.
- Do not add global response unwrapping or infer resource payloads from message-only responses.
- Project and task PATCH requests require the latest `version`; stale writes return 409 `edit_conflict`. Refresh the resource and let the user retry/reconcile.
- For pagination, send only validated canonical query values and follow returned `links.next`; preserve endpoint-specific compatibility such as meetings `request=previous`.
- Add an `Idempotency-Key` only through the existing dedicated helper for routes that currently use backend idempotency middleware. Keep database operation idempotency authoritative for subscription flows; do not add a global header interceptor.
- `alertNotice.performAction()` reads `response.data.message` directly and unconditionally redirects to `/dashboard`; it must be updated to use `getResponseMessage(response)` and accept an explicit redirect target. Do not call `performAction()` for actions that should not navigate away.

### Pre-release checklist

- [ ] Fix every P0 item and add focused regression coverage for each corrected behavior.
- [ ] Run `npm test`, `npm run lint`, and `npm run build`; investigate failures rather than treating build success as runtime proof.
- [ ] Smoke-test registration, login, logout, password reset, email verification/resend, 2FA challenge and settings, dashboard/chart, project/task CRUD and edits, invitations, meetings, notifications, subscriptions, tokens, and admin access in production-like staging.
- [ ] For task/project edits, confirm success updates the local version; submit a stale version and confirm 409 recovery works without silently losing the user's changes.
- [ ] Verify no cross-account domain data survives logout/login; check persisted browser storage directly.
- [ ] Check browser console/network output for failed requests, unhandled promise rejections, cookie/CORS/CSRF issues, and broken asset URLs.
- [ ] Confirm production API base URL, HTTPS, cookie domain/SameSite/Secure settings, CSRF, CORS, websocket/Pusher configuration, and public asset build configuration.
- [ ] In a staging environment served over HTTPS, confirm that WebSocket connections (Pusher/Echo) succeed and that real-time events are delivered. Verify `forceTLS` resolves to `true` at runtime.
- [ ] Verify 2FA session expiry: log in, wait more than five minutes without completing the 2FA challenge, then navigate to `/2fa/code` and confirm the router redirects to `/login` and clears `twofa_pending` and `twofa_timestamp` from `localStorage`.
- [ ] Record staging environment, build identifier, commands/results, smoke-test outcomes, and any open provider/infrastructure checks. Leave unavailable real-provider checks explicitly open.

## P1 — Performance concern to address before or immediately after launch

- **Route code splitting**: `resources/js/router.js` statically imports all 15+ page components, so every user downloads the entire app bundle on first load regardless of which page they visit. Convert route-level imports to dynamic `() => import(...)` calls. This directly impacts Time-to-Interactive on first load and is a visible quality signal to users. If a full lazy-load pass is not completed before launch, apply it at minimum to the heaviest components (`ProjectPage.vue`, `Subscription.vue`, `TwoFactorAuth.vue`, `AdminPanel`) as a first pass.

## P2 — Can follow after launch

These are valuable maintenance/performance improvements but are not release blockers unless they reveal a concrete defect:

- Centralize more Axios calls in domain services and reduce transport/payload logic in components.
- Reduce event-bus/global-mixin coupling and replace direct DOM lookups with refs where practical.
- Expand endpoint-matrix detail for lower-traffic admin and edge-case endpoints after all production-critical routes are covered.

## Evidence and scope

The 2026-09-30 review compared current Vue call sites with Laravel routes, request validation, resources, and frontend configuration. It was static inspection only.

The 2026-10-19 live code review read the actual source files (`bootstrap.js`, `router.js`, `store/index.js`, `store/currentUser`, `mixins/alertNotice.js`, `mixins/errorHandling.js`, `app.js`, `components/Project/Panel/Modal/TopArea.vue`, `components/Project/Panel/Features.vue`, `components/Authentication/Register.vue`, `components/Authentication/ResetPassword.vue`, `components/Dashboard/ProjectChart.vue`) and found that two original P0 items (`TopArea.vue` version send, `Features.vue` response parsing) were partially or fully addressed in code, and identified four additional issues not present in the original plan: the `forceTLS` hardcoded boolean, the `twofa_timestamp` string coercion bug, the `alertNotice.performAction` raw response read, and the missing route code-splitting. The two most critical of these are now P0; the response utility violation is captured in the API contract rules; route splitting is promoted to a tracked P1.

No production or staging browser smoke test has been run as part of either review. The separate backend Phase 4 production-readiness plan remains separate because its MySQL, Redis, queue, scheduler, Zoom, and Paddle checks are backend/infrastructure release gates.
