## Step 4: Task and Project Concurrency Documentation

### Optimistic Concurrency Control (P2.5 Contract)

Both task and project updates require optimistic concurrency control using a `version` field to prevent silent overwrites from concurrent edits.

### Version Field Requirements

**Project Update Request** (`PATCH /api/v1/projects/{project}`)

- `version` is **required**
- Type: integer
- Minimum: 1
- Purpose: Prevents silent overwrites from concurrent edits

**Task Update Request** (`PATCH /api/v1/projects/{project}/tasks/{task}`)

- `version` is **required**
- Type: integer
- Minimum: 1
- Purpose: Prevents silent overwrites from concurrent edits

### Server-Side Concurrency Handling

**Implementation in Services:**

1. **Database Transaction with Lock:**
   - Service re-fetches the resource with `lockForUpdate()` to ensure fresh state
   - This prevents race conditions during the update

2. **Version Check:**
   - Server compares the client-provided version with the current database version
   - If versions don't match, an `EditConflictException` is thrown

3. **Version Increment:**
   - On successful update, the version is automatically incremented
   - Client must fetch the new version for subsequent edits

### Edit Conflict Response

When a version mismatch occurs, the server returns:

**HTTP Status:** `409 Conflict`

**Response Body:**

```json
{
  "message": "The resource was modified by another user.",
  "code": "edit_conflict",
  "errors": [],
  "meta": {
    "expected_version": 5,
    "current_version": 6
  }
}
```

**Error Code:** `edit_conflict`

**Meta Fields:**

- `expected_version`: The version the client provided (stale)
- `current_version`: The actual current version in the database

### Frontend Requirement

Every task and project edit must:

1. Send the latest `version` received from the API
2. Handle `409 Conflict` responses by:
   - Refreshing the resource to get the current version
   - Showing the user that the resource was modified
   - Allowing the user to retry with the updated version

## Step 5: Zoom and Paddle Pending Outcomes Documentation

### Zoom Integration

#### Meeting Creation (`POST /api/v1/projects/{project}/meetings`)

**Uncertain Outcome Scenario:**
When the Zoom API returns an uncertain result (FatalRequestException, HTTP 500+ errors, or error code 0), the system:

1. **Immediate Response:**
   - HTTP Status: `202 Accepted`
   - Error Code: `zoom_meeting_creation_unknown`
   - Message: "Meeting creation is being processed. The meeting status will be updated shortly."
   - Meta: `{ "provider": "zoom", "reason": "creation_result_uncertain" }`

2. **Database State:**
   - Meeting sync status: `CreateUnknown`
   - `sync_available_at`: Set to 1 minute in the future
   - `sync_lease_expires_at`: Cleared
   - `sync_claim_token`: Cleared
   - Error details logged

3. **Client Behavior:**
   - **Do not retry** with the same operation ID
   - **Poll** the meeting endpoint to check sync status
   - Wait for webhook reconciliation (Zoom webhooks will confirm the actual state)
   - When status becomes `Active`, the meeting was successfully created
   - When status becomes `Failed`, the meeting creation failed

4. **Recovery:**
   - Background scheduler processes meetings with `CreateUnknown` status after `sync_available_at`
   - Webhook reconciliation can resolve the state
   - If remote meeting ID conflicts with webhook response, meeting requires manual recovery
   - Manual recovery endpoint available for ambiguous cases

**Successful Creation:**

- HTTP Status: `200 OK`
- Meeting sync status: `Active`
- Zoom meeting ID, start_url, join_url populated

**Failed Creation:**

- HTTP Status: `4xx` or `5xx` (depending on error)
- Meeting sync status: `Failed`
- Error details in `sync_error` field
- Client may retry after fixing the issue

#### Meeting Update (`PATCH /api/v1/projects/{project}/meetings/{meeting}`)

**Uncertain Outcome:**

- No special handling for uncertain outcomes
- On any failure, status set to `UpdateFailed`
- Client should retry the update operation

**Successful Update:**

- HTTP Status: `200 OK`
- Meeting sync status: `Active`
- Updated fields saved

**Failed Update:**

- HTTP Status: `4xx` or `5xx`
- Meeting sync status: `UpdateFailed`
- Error details in `sync_error` field
- Client should retry

#### Meeting Deletion (`DELETE /api/v1/projects/{project}/meetings/{meeting}`)

**Special Case - 404 Not Found:**

- Treated as success (meeting already deleted in Zoom)
- HTTP Status: `200 OK`
- Meeting sync status: `Deleted`

**Failed Deletion:**

- HTTP Status: `4xx` or `5xx`
- Meeting sync status: `DeleteFailed`
- Error details in `sync_error` field
- Client should retry

### Paddle Integration

#### Subscription Swap (`PUT /api/v1/users/me/subscription`)

**Operation Flow:**

1. Client provides idempotency key
2. System checks for existing operation with same idempotency key
3. If found, returns existing operation result
4. If not found, creates new operation with status `Processing`
5. Calls Paddle API

**Uncertain Outcome Scenario:**
When Paddle API call fails with non-PaddleException (network error, timeout, etc.):

1. **Immediate Response:**
   - HTTP Status: `200 OK` (operation recorded)
   - Message: "Your request is being processed. We will confirm the result shortly."
   - Operation status: `Unknown`
   - `available_at`: Set to 1 minute in the future

2. **Database State:**
   - Operation status: `Unknown`
   - Error details logged
   - `available_at`: Set for recovery

3. **Client Behavior:**
   - **Wait** for webhook reconciliation
   - **Do not retry** with the same idempotency key (will return existing operation)
   - Poll operation status if needed
   - When status becomes `Completed`, operation succeeded
   - When status becomes `Failed`, operation failed

**Paddle Rejection (PaddleException):**

- HTTP Status: Custom exception (usually 4xx or 5xx)
- Operation status: `Failed`
- Error details logged
- Client may retry with a new idempotency key

**Successful Swap:**

- HTTP Status: `200 OK`
- Operation status: `Completed`
- Message: "Your subscription has been successfully updated to the {plan} plan"

**Active Operation Conflict:**

- HTTP Status: `409 Conflict` (via ActiveOperationConflictException)
- Message: "Another operation is already in progress"
- Client must wait for current operation to complete

#### Subscription Cancel (`DELETE /api/v1/users/me/subscription`)

**Operation Flow:** Same as swap (idempotency key, operation tracking)

**Uncertain Outcome:** Same as swap (status `Unknown`, webhook reconciliation)

**Successful Cancel:**

- HTTP Status: `200 OK`
- Operation status: `Completed`
- Message: "Your subscription has been canceled successfully."

**Failed Cancel:**

- HTTP Status: Custom exception
- Operation status: `Failed`
- Error details logged
- Client may retry with new idempotency key

### General Patterns

**Idempotency:**

- Paddle operations require idempotency key
- Same idempotency key returns existing operation result
- Different idempotency key for same action plan throws `IdempotencyMismatchException`

**Webhook Reconciliation:**

- Both Zoom and Paddle use webhooks to confirm actual provider state
- Webhooks update operation/meeting status based on provider confirmation
- Client should wait for webhook reconciliation for uncertain outcomes

**Manual Review:**

- Some ambiguous Zoom meeting states may require manual resolution
- Manual recovery endpoints available for admin intervention

**Rate Limiting:**

- Zoom API rate limits return `429 Too Many Requests` with `retry_after_seconds` in meta
- Client should respect retry-after header

## Step 7: OpenAPI Failures Resolution

### Issue Analysis

The documentation tests reported three failures:

1. Missing `401` for `PUT /v1/projects/{project}`
2. Missing `422` for `PUT /v1/projects/{project}/tasks/{task}`
3. Missing `409` for `PUT /v1/projects/{project}/tasks/{task}`

### Root Cause and Resolution

Project and task updates are intentionally registered as PATCH-only routes because their request objects implement partial-update semantics. The documentation tests still expected the older PUT contract. The tests now assert the registered PATCH method. PUT/PATCH duplication remains supported only for resources that actually register both methods at runtime.

### Fix Applied

**Files:** `tests/Feature/Api/Contracts/Docs/ScrambleDocsTest.php` and generated `api.json`.

The route contract was corrected at its source: project and task updates are PATCH-only, while resources that actually register both methods (such as users) retain both PUT and PATCH documentation. The test expectations now match the runtime route table, and the generated contract no longer invents PUT operations for PATCH-only project and task updates.

### Existing Error Response Mechanisms

The application already has robust error response generation:

1. **PublicApiResponses** - Registers shared error response schemas and ensures all operations have appropriate error responses
2. **PublicApiMiddlewareResponses** - Adds middleware-aware error responses (403 for token abilities/policies, 429 for throttling, idempotency responses)
3. **ApiError attributes** - Controllers use `#[ApiError(ErrorCode::EDIT_CONFLICT)]` to document business errors
4. **EditConflictException** - Already properly documented with 409 status in ErrorCode registry
