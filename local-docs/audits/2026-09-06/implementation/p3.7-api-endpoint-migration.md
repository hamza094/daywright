# P3.7: API Endpoint Migration to REST-style Endpoints

## Overview

This document describes the completed migration from action-style endpoints to resource-oriented REST endpoints for the Daywright API v1. The migration was completed on 2026-09-06, with all legacy endpoints and backward compatibility code removed.

## Migration Summary

### 1. Task Assignment

**Old Endpoint (Removed):**

- `PATCH /api/v1/projects/{project}/tasks/{task}/assign`
- Request body: `{ "members": [3, 5] }`

**Current Endpoint:**

- `POST /api/v1/projects/{project}/tasks/{task}/assignees`
- Request body: `{ "user_ids": [3, 5] }`

**Changes:**

- HTTP method changed from `PATCH` to `POST` (REST semantics for creating relationships)
- Request field changed from `members` to `user_ids` for clarity
- Route name changed from `api.v1.task.assign` to `api.v1.task.assignees.store`

**Backend Status:**

- Legacy route removed
- `TaskMembersRequest` only accepts `user_ids` field
- Controller: `StoreTaskAssigneesController`

**Frontend Status:**

- `TaskMembers.vue` uses `POST /assignees` with `user_ids`

---

### 2. Task Unassignment

**Old Endpoint (Removed):**

- `PATCH /api/v1/projects/{project}/tasks/{task}/unassign`
- Request body: `{ "member": 3 }`

**Current Endpoint:**

- `DELETE /api/v1/projects/{project}/tasks/{task}/assignees/{user}`
- Request body: None (user ID in route parameter)

**Changes:**

- HTTP method changed from `PATCH` to `DELETE` (REST semantics for deleting relationships)
- User ID moved from request body to route parameter
- Route name changed from `api.v1.task.unassign` to `api.v1.task.assignees.destroy`

**Backend Status:**

- Legacy route removed
- Controller: `DestroyTaskAssigneeController`
- Idempotency middleware removed (DELETE endpoint should not be idempotent)

**Frontend Status:**

- `TaskDetailModal.vue` uses `DELETE /assignees/{memberId}`

---

### 3. Bulk Project Deletion

**Old Endpoint (Removed):**

- `DELETE /api/admin/v1/projects/bulk-delete`
- Request body: `{ "project_ids": [1, 2] }`

**Current Endpoint:**

- `DELETE /api/admin/v1/projects`
- Request body: `{ "ids": [1, 2] }`

**Changes:**

- Endpoint simplified to collection route (REST semantics)
- Request field changed from `project_ids` to `ids` for consistency
- Route name changed from `api.v1.admin.projects.bulk-delete` to `api.v1.admin.projects.destroyMany`

**Backend Status:**

- Legacy route removed
- `ProjectBulkDeleteRequest` only accepts `ids` field
- Controller: `ProjectController::bulkDelete()`

**Frontend Status:**

- `Projects.vue` uses `DELETE /admin/projects` with `ids`

---

### 5. Two-Factor Status

**Old Endpoint (Removed):**

- `GET /twofactor/fetch-user`

**Current Endpoint:**

- `GET /twofactor/status`

**Changes:**

- Endpoint renamed for clarity (REST semantics)

## Implementation Details

### Controllers Created

1. `StoreTaskAssigneesController` - Handles POST /assignees
2. `DestroyTaskAssigneeController` - Handles DELETE /assignees/{user}

### Request Classes Updated

1. `TaskMembersRequest` - Now only accepts `user_ids` field
2. `ProjectBulkDeleteRequest` - Now only accepts `ids` field
3. `TaskBulkDeleteRequest` - Now only accepts `ids` field

### Request Classes Removed

1. `TaskMemberUnassignRequest` - No longer needed (user ID in route parameter)
2. `TaskAssigneeStoreRequest` - Replaced by `TaskMembersRequest`
3. `TaskAssigneeDestroyRequest` - No longer needed (validation in controller)

### Controllers Removed

1. `AssignTaskMembersController` - Replaced by `StoreTaskAssigneesController`
2. `UnassignTaskMemberController` - Replaced by `DestroyTaskAssigneeController`

- All legacy routes removed
- All backward compatibility logic removed from request classes
- All deprecated controllers removed
- All tests updated to use new endpoints only

**Breaking Changes:**

- Legacy endpoints are no longer available
- Legacy field names (`members`, `project_ids`, `task_ids`) are no longer accepted

## Breaking Changes

**For API Consumers:**

- Legacy endpoints are no longer available
- Must use new REST endpoints
- Must use new field names (`user_ids`, `ids`)

**For Frontend:**

- Frontend has been fully migrated to new endpoints
- No breaking changes for users

---

## Rollback Plan

If issues arise with the new endpoints:

1. This migration is complete and cannot be rolled back without code changes
2. To restore legacy endpoints, revert the route file changes
3. To restore backward compatibility, revert request class changes
4. No data migration or schema changes required
